# Phase 0 Research: Clock Divider

## Decision: Follow StepSequencer's lookahead-scheduler pattern, generalized to 6 independent `nextTickTime`/interval pairs sharing one `setInterval` poll loop

**Rationale**: This codebase has two distinct BPM-driven scheduling mechanisms already in production:
- **StepSequencer** (`src/components/utilities/StepSequencer.ts:44-46,467-469,509-543`): a drift-resistant "lookahead" scheduler — `nextStepTime` (a running `AudioContext.currentTime`-space cursor) is advanced by a freshly-recomputed `stepInterval` inside a `while (nextStepTime < currentTime + lookaheadTime)` loop, itself polled every 25ms via `setInterval`. Because `nextStepTime` is *never reset* on a BPM change — only the increment added to it changes — a live BPM change takes effect on the very next loop iteration with no phase discontinuity.
- **Arpeggiator** (`src/components/utilities/Arpeggiator.ts:88-94,261-264`): a naive `setInterval(() => tick(), intervalMs)` that is fully torn down and restarted on every BPM change, causing a phase jump.

The spec's edge case "global BPM changes while a division is actively counting mid-cycle... MUST re-lock... without producing a spurious extra or missing pulse" (spec.md Edge Cases) and SC-002 ("no audible or measurable drift... after several minutes") both rule out the Arpeggiator's restart-based approach and require StepSequencer's approach. Since Clock Divider needs **6 simultaneous, independently-rated outputs that must stay phase-coherent with each other** (FR-007, spec's US3 acceptance scenario 2: "/2 and /4... always land on a beat where /2 also pulses"), the natural generalization is: one `nextTickTime[i]` + one `intervalMs[i]` pair per output (i = 0..5), all six advanced inside the *same* 25ms-polled `while` loop, all six intervals recomputed from the *same* shared `bpm` value on every poll. Because all six intervals are exact rational multiples of the same underlying beat duration (via `TimingCalculator.beatsToMs`, see below), a /2 output and a /4 output derived from the same origin time are mathematically guaranteed to coincide on every beat where /4 fires, satisfying FR-007 by construction rather than by additional synchronization logic.

**Alternatives considered**:
- *Arpeggiator's `setInterval`-per-tick restart pattern*: rejected — phase-discontinuous on BPM change, and with 6 independent intervals this would mean 6 separate `setInterval` timers restarting independently, which cannot guarantee the /2-vs-/4 coincidence relationship the spec requires.
- *One `setInterval` per output (6 timers total) instead of one shared loop*: rejected — six independent JS timers firing async introduce ordinary browser timer jitter *relative to each other*, undermining exact beat coincidence; a single shared 25ms poll loop that recomputes all six `nextTickTime`s from one clock origin is what makes the coincidence guarantee possible.

## Decision: Six independent `ConstantSourceNode` gate outputs via a `getOutputNodeByPort` override, following ChordFinder's multi-output pattern

**Rationale**: No existing component has 2+ simultaneous independently-driven gate outputs (confirmed: Arpeggiator and StepSequencer each expose exactly one gate output). The closest and only viable precedent for "N independently-wired outputs of the same signal type from one component" is **ChordFinder** (`src/components/utilities/ChordFinder.ts:99-103,197-206`), which exposes 3 CV outputs plus a gate output, each backed by its own dedicated `AudioNode` field, selected via an overridden `protected getOutputNodeByPort(portId: string): AudioNode | null` switch statement — the base class's default implementation (`SynthComponent.ts:329-333`) just falls back to the single main output, which is insufficient once there's more than one port of the same signal type. Clock Divider will declare 6 private `ConstantSourceNode | null` fields (one per rate output), create+start+`registerAudioNode` each in `createAudioNodes()`, call `addOutput(portId, label, SignalType.GATE)` six times in the constructor, and override `getOutputNodeByPort` with a switch mapping each port ID to its node — directly mirroring ChordFinder's shape.

**Alternatives considered**:
- *A single gate output with a "selected rate" dropdown, requiring 6 separate Clock Divider instances for 6 rates*: rejected — this contradicts FR-003 and spec User Story 3 explicitly ("without adding a separate Clock Divider... for each rate"), which is the feature's stated differentiator.
- *A single POLY_CV-style bundled output carrying all 6 rates, unbundled downstream*: rejected — no existing gate-consuming component in this project (ADSREnvelope, KarplusStrong, Collider, Arpeggiator) knows how to unbundle a poly-style gate signal; every gate consumer expects a plain `SignalType.GATE` port. Introducing an unbundling contract would require changes to every existing gate-consuming component, far exceeding this feature's scope.

## Decision: Persist each output's rate as a separate numeric parameter (`rate1`…`rate6`), indexing into a `ClockDividerRate` enum — reusing the exact pattern already used for Arpeggiator's `subdivision` and Collider's `bpmMode`

**Rationale**: `SynthComponent.serialize()`/`deserialize()` (`src/components/base/SynthComponent.ts:513-544`) are fully generic — they persist *every* parameter as a plain number in `ComponentData.parameters: Record<string, number>`, with no special-casing anywhere in the codebase for enum-like choices. Arpeggiator's `subdivision` parameter (`specs/029-arpeggiator/contracts/types.ts:16-21,55`) is a numeric enum index (`ArpSubdivision.Quarter = 0`, etc.) persisted this way, as are StepSequencer's `noteValue`/`bpmMode` and Collider's `scaleType`/`bpmMode`/`gateSize`. Clock Divider's 6 independent rate choices follow the identical, already-proven shape: `addParameter('rate1', 'Output 1 Rate', defaultIndex, 0, N-1, 1, '')` through `rate6`, each an index into a shared `ClockDividerRate` enum (e.g. `Div16=0, Div8=1, Div4=2, Div2=3, X1=4, X2=5, X3=6`), with a parallel `RATE_BEATS_PER_PULSE: Record<ClockDividerRate, number>` lookup — directly modeled on `ArpSubdivision`'s parallel `SUBDIVISION_FRACTIONS` map. This satisfies FR-009 (persist/restore per-output settings) using zero new serialization machinery.

**Alternatives considered**:
- *A single `outputs: string` JSON-blob parameter encoding all 6 rates at once*: rejected — every other multi-choice component in this codebase (Arpeggiator, StepSequencer, Collider) persists each choice as its own named numeric parameter; introducing a JSON-blob field would be the first of its kind and would need bespoke serialize/deserialize logic that the generic `Record<string, number>` mechanism doesn't need.

## Decision: Compute each output's pulse period via `TimingCalculator.beatsToMs(bpm, beatsPerPulse)`, not `calculateGateDuration`

**Rationale**: `TimingCalculator.calculateGateDuration(bpm, gateSize)` (`src/timing/TimingCalculator.ts:23-38`) is semantically scoped to *envelope gate lengths* and only accepts fraction-of-quarter-note values below 1 (whole/half/quarter/eighth/sixteenth, per `getAllGateDurations`'s hardcoded fraction list) — it has no concept of multiplication (x2, x3), which FR-005 requires. `beatsToMs(bpm, beats)` (`TimingCalculator.ts:69-72`) is the general-purpose primitive that already exists for exactly this: passing `beats = 4` yields the period of a /4 pulse, `beats = 0.5` yields the period of an x2 pulse, `beats = 1/3` yields an x3 pulse — one existing function covers the entire /2…/16, x2, x3 range with no new BPM math needing to be written or tested.

**Alternatives considered**:
- *Extending `calculateGateDuration`/`GateSize` to also accept multiplier fractions > 1*: rejected — `GateSize` is a shared type imported from `specs/006-collider-musical-physics/contracts/types` and used by Collider's gate-length UI; broadening its semantics to double as a general beat-period calculator would conflate two different concepts (envelope gate length vs. clock pulse period) and risk regressing Collider's existing gate-size behavior. `beatsToMs` already exists, is unused by any multiplier-needing feature yet, and cleanly fits.

## Decision: Pulse *width* (how long the gate stays high) is a fixed proportion of each output's own period — a 25% duty cycle — not a fixed millisecond value

**Rationale**: An earlier draft of this plan proposed a fixed 10ms high pulse (`setValueAtTime(1, t)` then `(0, t + 0.01)`) on the claim that it "matches StepSequencer's gate-on/off pattern" (`/speckit-analyze` finding U1). That claim does not hold up against the actual code: StepSequencer's gate-off time is **not** a fixed duration — `getGateDuration(step, stepInterval)` (`StepSequencer.ts:446-452`) computes `stepInterval / 2^(gateLength-1)`, i.e. a proportion of that step's own interval (e.g. 50%, 25%, 12.5% of the step, depending on the per-step `gateLength` setting), so the pulse width scales with tempo and rate rather than being a constant. A fixed 10ms pulse would become disproportionately long relative to a fast X3 output's period at high BPM (a period of ~111ms at 180 BPM would spend ~9% of its cycle high — borderline but survivable) and, more importantly, disproportionately *short* relative to a slow /16 output's period (7.5 seconds at 60 BPM — a 10ms blip is 0.13% of the cycle), which risks the pulse being missed entirely by any consumer whose `AnalyserNode`/scheduler polling cadence doesn't happen to land within that narrow window. Following StepSequencer's actual proportional-duration convention instead: each output's pulse stays high for 25% of *that output's own* period (`ratePeriodMs(bpm, rate) * 0.25`), computed via a new `pulseWidthMs(bpm, rate)` helper in `contracts/validation.ts`, alongside the existing `ratePeriodMs`. 25% is chosen as a clear, unambiguous duty cycle (comfortably longer than StepSequencer's shortest gate-length option, comfortably shorter than a fully "held" gate) that scales correctly across all six rates and any BPM.

**Alternatives considered**:
- *Fixed 10ms pulse (the original proposal)*: rejected per the analysis above — not actually grounded in StepSequencer's real behavior, and risks reliability problems at both ends of the six rates' period range.
- *50% duty cycle (square wave, matching a literal "clock" signal)*: considered viable, but 25% more closely matches StepSequencer's default/typical gate-length settings and leaves more headroom before the next pulse at the fastest configured rate (X3), reducing any risk of overlapping on/off scheduling calls at high BPM.

## Decision: Subscribe to `GLOBAL_BPM_CHANGED`, `TRANSPORT_PLAY`, and `TRANSPORT_STOP` in `createAudioNodes()`/`destroyAudioNodes()`, matching StepSequencer's lifecycle exactly; no local/global BPM mode toggle

**Rationale**: Both `GLOBAL_BPM_CHANGED` subscription (`StepSequencer.ts:368-378`, `Collider.ts:251-261`) and transport subscription (`StepSequencer.ts:390-410`, `Looper.ts:159-178`) follow the same lifecycle convention in every existing `TempoAware` component: subscribe when audio nodes are created, unsubscribe when destroyed, store the unsubscribe closure in a private field. On `TRANSPORT_STOP`, StepSequencer clears its scheduling interval and zeroes its gate node via `setValueAtTime(0, ctx.currentTime)` without resetting phase; Clock Divider will do the same for all 6 gate nodes. Per spec.md's Assumptions ("The Clock Divider follows the shared global tempo... it is not driven by an external incoming clock/gate signal"), there is **no `bpmMode` parameter** — Clock Divider always follows global BPM unconditionally, closer to Arpeggiator's model (always-global, no toggle) than StepSequencer/Collider's (toggleable). This is a deliberate simplification consistent with the spec's own scope boundary, and avoids exposing a "local BPM" concept that has no meaning for a component whose entire purpose is deriving rates *from* the shared tempo.

**Alternatives considered**:
- *Adding a `bpmMode` toggle for symmetry with StepSequencer/Collider*: rejected — the spec's Assumptions section explicitly scopes this feature to global-tempo-only; a component whose sole purpose is "divide/multiply the shared clock" has no coherent "local tempo" mode to toggle into (what would "local" even multiply?). Matching StepSequencer/Collider's toggle here would add a control with no clear meaning, contradicting the constitution's "avoid magic numbers/strings" and UI-consistency principles by adding a switch that doesn't switch between two meaningful states.

## Decision: Layout follows Arpeggiator's "N stacked dropdown rows" `calculateComponentHeight` special-case, generalized from 4 rows to 6

**Rationale**: `getControlLayout()`'s generic `hasDropdown` path (`src/utils/componentLayout.ts:449-454`) only budgets height for one dropdown row; every component needing more than one dropdown (StepSequencer, ChordFinder, Collider, Arpeggiator, ParametricEQ) already has its own bespoke `if (type === ComponentType.X)` block in `calculateComponentHeight()` (`componentLayout.ts:367-438`) — there is no generic "N dropdowns" layout primitive to extend; adding a per-type case is the established pattern, not a workaround. Arpeggiator's exact formula (`componentLayout.ts:422-429`): `HEADER_HEIGHT + portAreaHeight + CONTROL_MARGIN_TOP + dropdownRowHeight * rowCount + 10`, where `dropdownRowHeight = DROPDOWN_HEIGHT + CONTROL_SPACING_VERTICAL + 12 = 51`. For Clock Divider's 6 rows this becomes `... + 51*6 + 10`. Control instantiation itself happens in `CanvasComponent.createControls()` (`CanvasComponent.ts:802-877`, Arpeggiator's block is the template) via a loop placing one `Dropdown` per output at `baseY + rowH*i`.

**Alternatives considered**: None — this is a direct, low-risk generalization of an existing, already-proven pattern (Arpeggiator's own layout code), not a new design.

## Decision: No maximum-output-count guardrail beyond the fixed 6; no minimum-output guardrail either (all 6 always present)

**Rationale**: Per spec.md's Assumptions ("a small, fixed set... not user-extendable... exact output count is a reasonable implementation default not mandated by this spec"), 6 outputs (four common divisions — /2, /4, /8, /16 — plus two common multiplications — x2, x3 — matching FR-004/FR-005's stated minimums exactly, one output per named rate) is the natural default: it's the smallest set that satisfies every explicitly-named rate in the spec with no arbitrary additions, and keeps the component's canvas footprint bounded (6 rows, comparable to Arpeggiator's 4-row layout generalized).

**Alternatives considered**: None — the spec explicitly defers exact count to implementation judgment; 6 (one row per FR-004/FR-005's named rate) is the most defensible default since it introduces no unrequested scope.
